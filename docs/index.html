Nine tiers, from schema linking to multi-turn sessions, including a tier whose correct answer is that the question cannot be answered from the data. Every row below was executed by the organizers, and every score is a mean over repeated runs.

Why the board ranks on Pass^N. Two identical runs of the same agent — same model, same questions, temperature 0 — disagreed on 21% of tasks. Ranking on the average would reward a system that is often right and never reliably right, so the ranking metric is the one a buyer actually cares about: solved every time. The gap between Pass@N and Pass^N is churn, and it is large for every system measured so far. Every individual run's score is published in the entry file, including the bad ones.

Two denominators, on purpose. Pass^N and Pass@N are over the 190 tasks attempted, because reliability is only meaningful about work a system took on. EX is over all 190, because a system must not be able to raise its headline by declining the hard questions. Both are shown so neither can be quoted alone.

Neo-Cortex carries a Legacy pill because it was measured against an earlier data snapshot. Gold answers are bound to the snapshot they were compiled from, so that figure is real but not comparable with the ranked rows, and it takes no rank. Its captured SQL cannot be re-executed either — the agent emitted parameterised SQL whose bound values were never recorded — so a comparable number needs the agent re-run, not the capture re-scored.

A dash is not a zero. Hover it to see why the metric was not measured.

03

Multi-turn: sessions, not turns

The 41 tier-9 turns belong to 8 conversations. Each turn is handed the agent’s own SQL from the previous turn — right or wrong, never corrected, never gold. An error on turn 2 is inherited by turn 3, which is the point: this measures whether a system can hold a conversation, not whether it can answer a question. Session success rate counts a session only when every turn in it passes on every run.

Cells are turns solved on every run, out of the turns in that session. ✓ marks a session where every turn passed — the only thing that counts toward SSR. Sessions are labelled rather than named: six run to 4 turns, one to 8 and one to 9. The tasks themselves are held out, so they are described and not identified.

SSR is deliberately harsh, and the per-session cells are why it is shown alongside them rather than alone: a system that solves 6 of 8 turns and one that solves 0 of 8 both score a failed session, and those are not the same system. Read the cells for capability and the SSR column for reliability.

04

Cost and latency against accuracy

What each system spends to get where it got. Rows are ordered by accuracy, best at the top, and the dot is what that system spent — so read down for accuracy and across for spend. A dot far to the right on a row near the bottom is paying for nothing. Correctness alone is not the whole picture on a 58-million-row database — a query that returns the right answer in six minutes is not a usable one.

Commercial band ‡ — ships its own model Controlled arm — one fixed base model

The cost axis is logarithmic: each gridline is ten times the one before it. It has to be — the board spans $0.0019 to $1.7265 per task, a factor of 909, and on a linear axis six of the seven systems sit on the baseline. The marks are dots rather than bars for the same reason: a bar's length is a claim about ratio, and on a log axis that claim would be false. The latency axis is linear and starts at zero.

Latency and cost come from the live agent runs. Neither is currently folded into the score: an efficiency metric in the spirit of BIRD's VES is on the roadmap, and until it exists a slow correct answer ranks exactly like a fast one.

Cost is not one meter. These figures are comparable within a band, not across the column. The gpt-5.6-luna rows are billed per token and measured per task. Claude Code's is API-equivalent rather than billed — nothing was charged. Snowflake Cortex Analyst reports no per-request cost at all and is billed per message at a flat rate rather than per token, so its figure is derived from account-level credit metering and is insensitive to how much context each call carried. Databricks Genie is derived the same way from DBU metering, and is the one figure on the board priced at a rate the account was not actually charged — Genie was free during the run, so the rate is the vendor's published one for equivalent compute. It is also the only row whose cost includes executing every query against the full warehouse. Each row's notes field in results/ states exactly how its number was obtained. Read them before quoting a ratio between two rows.

Method, in brief

190 execution-scored questions, 9 tiers, one frozen snapshot.
Gold answers compiled by executing reference SQL against that snapshot.
Synthetic data: deterministic, seed 42, FK-integrity validated, no PII.
Scored by eval/score_cortex_bench.py, unmodified, by the organizers.
Every run's score published, including the bad ones.

Each row on this board is a JSON file in results/, validated in CI against schema/leaderboard_entry.schema.json. This page is regenerated from those files and holds no data of its own — edit the JSON, never the HTML. The provenance of any number is git log results/<entry-id>.json.
